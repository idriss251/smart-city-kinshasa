================================================================================
CHAPITRE 3 : RÉALISATION DU NOUVEAU SYSTÈME
================================================================================

Ce chapitre détaille la mise en œuvre technique de la plateforme Smart City
Kinshasa. Il présente les captures d'écran des interfaces utilisateur et
explique les aspects techniques du développement.

================================================================================
3.1 ARCHITECTURE GLOBALE DU SYSTÈME
================================================================================

Le système est basé sur une architecture microservices déployée avec Docker.
L'orchestration est gérée par docker-compose qui définit 20+ conteneurs
incluant :
- API Gateway (Spring Cloud Gateway) - Port 18080
- Eureka Server (Service Discovery) - Port 18761
- 5 Microservices Spring Boot (Auth, Waste, Road, Flood, Dashboard)
- 5 Bases de données PostgreSQL avec PostGIS
- Infrastructure : Redis (cache), RabbitMQ (messaging), Mosquitto (MQTT)
- Frontend React avec Nginx - Port 13000

La communication entre services se fait via REST API, avec routage dynamique
assuré par l'API Gateway. Le service discovery avec Eureka permet aux
microservices de s'enregistrer et de se découvrir automatiquement.

================================================================================
3.2 DÉVELOPPEMENT DES MICROSERVICES
================================================================================

Les microservices sont développés avec Spring Boot 3.x et Java 17. Chaque
service suit une architecture en couches standard :

3.2.1 Service d'Authentification
----------------------------------
Gère l'authentification et l'autorisation avec JWT. Inclut :
- Modèles : User, Role (ADMIN, AGENT, CITOYEN, DECIDEUR)
- Sécurité : BCrypt pour le hachage des mots de passe
- JWT : Token generation et validation
- Endpoints : POST /auth/login, POST /auth/register

3.2.2 Service de Gestion des Déchets
---------------------------------------
Gère les poubelles intelligentes et les collectes. Inclut :
- Modèles : GarbageBin (niveau_remplissage, statut), Collection
- Fonctionnalités : Surveillance niveau poubelles, planification collectes
- Endpoints : CRUD sur /api/waste

3.2.3 Service de Gestion des Routes
------------------------------------
Gère les problèmes routiers et les interventions. Inclut :
- Modèles : RoadProblem (type, gravite), Intervention
- Fonctionnalités : Signalement problèmes, tracking interventions
- Endpoints : CRUD sur /api/road

3.2.4 Service de Surveillance des Inondations
----------------------------------------------
Surveille les zones inondables avec capteurs IoT. Inclut :
- Modèles : FloodZone (niveau_actuel, seuil_alerte), FloodAlert
- Fonctionnalités : Monitoring temps réel, génération alertes automatiques
- Endpoints : CRUD sur /api/flood

3.2.5 Service de Dashboard
----------------------------
Agrège les statistiques de tous les services. Inclut :
- DTOs : DashboardStats, CommuneStats, EvolutionData
- Fonctionnalités : Calculs sur 24h, tendances, métriques système
- Endpoints : GET /api/dashboard/stats, /citizen-stats, /agent-stats, /admin-stats

================================================================================
3.4 CONFIGURATION DOCKER
================================================================================

L'orchestration Docker est définie dans docker-compose.yml avec :
- 20+ services interconnectés
- Réseau bridge pour la communication interne
- Volumes pour la persistance des bases de données
- Port mapping pour l'accès externe
- Multi-stage builds pour optimiser la taille des images

Chaque microservice a son propre Dockerfile avec :
- Étape build : Maven pour Java, npm pour React
- Étape runtime : JRE pour Java, Nginx pour React
- Optimisation : Caching des dépendances, minimisation

================================================================================
3.5 INTÉGRATION DES BASES DE DONNÉES
================================================================================

3.5.1 Configuration PostgreSQL
-------------------------------
Chaque microservice a sa propre base de données PostgreSQL 15 :
- authdb (Port 55433) : users, roles, permissions
- wastedb (Port 55434) : bins, collections, zones, schedules
- roaddb (Port 55435) : road_problems, interventions, roads, agents
- flooddb (Port 55436) : flood_zones, measures, alerts, sensors
- dashboarddb (Port 55439) : statistics, reports, aggregations

Les connexions sont configurées dans application.yml avec HikariCP
connection pooling pour optimiser les performances.

3.5.2 Migrations Flyway
-----------------------
La gestion des schémas de base de données est assurée par Flyway :
- Scripts SQL versionnés (V1__, V2__, etc.)
- Exécution automatique au démarrage
- Rollback supporté
- Déploiement des données de test (seed data)

3.5.3 Données PostGIS
----------------------
Les services géospatiaux utilisent l'extension PostGIS :
- gis-db : features géographiques (points, polygones)
- flood-db : zones inondables avec coordonnées
- roaddb : localisation des problèmes routiers
- wastedb : emplacement des poubelles
- Support des requêtes spatiales et calculs de distance

3.6 TESTS FONCTIONNELS
================================================================================

Les tests sont organisés en plusieurs niveaux :

3.6.1 Tests Unitaires
----------------------
- Framework : JUnit 5 + Mockito

3.6.2 Tests d'Intégration
--------------------------
- Tests d'intégration des API REST
- Tests avec bases de données H2 embarquées

3.6.3 Tests Manuels
--------------------
- Collection Postman pour les API
- Tests des interfaces utilisateur
- Validation des scénarios métier
- Tests de performance avec JMeter

3.7 DÉMONSTRATION DU TABLEAU DE BORD EN TEMPS RÉEL
================================================================================

Le dashboard en temps réel montre :
- Mise à jour automatique des données chaque minute
- Statistiques sur 24h avec graphiques d'évolution
- Alertes automatiques pour les seuils critiques
- Carte interactive avec les incidents en temps réel
- Simulation IoT via Python dans iot-simulation/

Le système génère des alertes automatiques quand :
- Niveau d'eau > seuil critique → alerte urgente
- Niveau poubelle > 90% → collecte urgente
- Nouveau signalement → notification agents

================================================================================
3.8 DÉPLOIEMENT ET MISE EN PRODUCTION
================================================================================

Le déploiement se fait via Docker Compose :
1. Build : docker compose build (construction des images)
2. Up : docker compose up -d (démarrage des conteneurs)
3. Vérification : docker compose ps (statut des services)
4. Accès : http://localhost:13000 (frontend)

Les services sont démarrés dans l'ordre :
- Infrastructure (Redis, RabbitMQ, Mosquitto)
- Bases de données (PostgreSQL)
- Eureka Server (service discovery)
- Microservices (enregistrement automatique)
- API Gateway et Frontend
